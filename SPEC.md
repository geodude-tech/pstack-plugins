# Spec: pstack-to-codex

## Objective

Build a local, dependency-free CLI that converts a checked-out Cursor `pstack` plugin into a separate plugin tree for another agent host. The converter is for engineers who want a reproducible starting point without trusting a third-party prebuilt port. It supports two targets, `codex` (default) and `claude`. Success means the generated tree is installable as a local marketplace plugin for the chosen target, preserves upstream attribution, and clearly reports every host-specific construct that was changed, omitted, or left for review — where "host-specific" is judged against the chosen target, not against Codex specifically.

## Tech Stack

- Node.js 20 or newer, ECMAScript modules
- Node's built-in test runner and standard library only
- JSON and Markdown output; no network access

## Commands

- Convert: `node ./bin/pstack-to-codex.js <source> --out <destination>`
- Preview: `node ./bin/pstack-to-codex.js <source> --out <destination> --dry-run`
- Test: `npm test`
- Syntax/build check: `npm run check`

## Project Structure

- `bin/` — executable CLI entry point
- `src/` — source discovery, conversion, rewriting, validation, and report generation
- `test/` — unit and filesystem integration tests
- `tasks/` — implementation plan and tracked checklist

## Code Style

```js
export function normalizePluginName(value) {
  return value.toLowerCase().replace(/[^a-z0-9]+/g, "-").replace(/^-|-$/g, "");
}
```

Use small pure functions where practical, explicit result objects instead of hidden global state, and structured error messages suitable for shell users.

## CLI Contract

```text
pstack-to-codex <source> --out <destination>
  [--target <codex|claude>]
  [--name <plugin-name>]
  [--force]
  [--dry-run]
  [--json]
```

- `<source>` may be the Cursor plugins repository root or its `pstack/` directory.
- `--out` is required and must not equal or be inside the source directory.
- Existing destinations are rejected unless `--force` is supplied.
- `--force` replaces only a destination previously generated by this tool, identified by a receipt file.
- `--dry-run` performs discovery and analysis without writing files.
- `--json` prints the conversion result as JSON; otherwise the CLI prints a concise human summary.
- Exit `0` on a completed conversion or successful preview, `1` for invalid input or failed conversion, and `2` when conversion completed with manual-review findings.

## Conversion Rules

1. Validate the Cursor manifest and required `skills/` tree.
2. Copy skills, docs, scripts, assets, licenses, and notices without following symlinks.
3. Exclude `.git`, Cursor manifests, Cursor-only agent definitions, and Cursor-only automations from executable discovery on the target host.
4. Generate the target's plugin manifest (`.codex-plugin/plugin.json` or `.claude-plugin/plugin.json`) and marketplace file (`.agents/plugins/marketplace.json` or `.claude-plugin/marketplace.json`) using valid shapes for that target.
5. Apply a small, explicit set of text substitutions for known host names and invocation syntax, using the sigil (or absence of one) that matches the target's own convention. Never guess replacements for tools or model identifiers.
6. Scan Markdown and scripts for Cursor-only paths, commands, tools, models, hooks, and automation references that remain unmapped **for the chosen target** — a construct the target already supports natively (e.g. Claude Code's own `AskUserQuestion`, `Agent` tool, `/loop` skill, and `claude-*` model names) is not a finding.
7. Write `compatibility/report.json`, `compatibility/report.md`, `NOTICE`, and `.pstack-to-codex.json` with source commit/version, target, copied files, rewrites, omissions, and unresolved findings.

## Testing Strategy

- Unit tests cover path validation, manifest translation, text rewriting, and finding classification.
- Filesystem integration tests convert synthetic Cursor plugin fixtures and assert the generated artifact.
- End-to-end tests exercise the CLI's human and JSON modes, dry-run behavior, conflict handling, and exit codes.
- Tests use temporary directories and never touch user plugin configuration.

## Boundaries

- Always: preserve source files, reject symlinks and unsafe paths, produce provenance, and default to non-destructive behavior.
- Ask first: installing the generated plugin, modifying a personal marketplace, fetching repositories, or replacing output not owned by this tool.
- Never: mutate the source clone, execute copied scripts, infer credentials, silently discard unsupported behavior, or claim semantic parity when findings remain.

## Success Criteria

- Converts both supported source layouts into a valid standalone plugin tree.
- Is deterministic for the same source and options except for recorded generation time.
- Never overwrites an unrelated directory, including with `--force`.
- Produces actionable reports for unsupported constructs.
- Passes all automated tests and a smoke conversion against a realistic fixture.
- Documents local marketplace installation and the limitations of mechanical conversion.

## Open Questions

- None blocking. The initial version intentionally reports uncertain semantic mappings instead of attempting them.
